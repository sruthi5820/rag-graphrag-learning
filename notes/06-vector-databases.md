
# Lesson 6: Vector Databases

## 6.1 What Is a Vector Database?

A **vector database** is a database system designed to store, index, and search numerical vectors efficiently.

In AI applications, embedding models convert text into numerical vectors. A vector database helps find vectors that are similar to a user's query vector.

In a Retrieval-Augmented Generation (RAG) system, a vector database commonly stores document embeddings along with the original text and metadata.

### Example

Suppose a document contains:

```text
Users can recover their account through password reset.
```

An embedding model converts the text into a numerical vector.

The vector database stores the vector together with the document text and its metadata.

When a user asks a related question, the application searches for similar vectors and retrieves the associated document text.

### Example Record

```json
{
  "id": "doc-001-chunk-003",
  "text": "Users can recover their account through password reset.",
  "metadata": {
    "source": "account-guide.md",
    "page": 2,
    "chunk_index": 3
  }
}
```

The embedding vector is not shown in this example.

### Why Do We Need a Vector Database?

A vector database helps an application:

- Store document embeddings.
- Search for semantically related content.
- Retrieve relevant document chunks.
- Filter results using metadata.
- Update and delete stored records.
- Persist data between application runs.
- Search large collections more efficiently than a simple linear scan, depending on the index and configuration.

### Key Learning

A vector database stores and searches vectors. In RAG, it helps retrieve relevant text for a user's question.

## 6.2 What Is a Vector?

A vector is an ordered collection of numerical values.

Example:

```text
[0.12, -0.08, 0.41, 0.27, -0.16]
```

This vector has five dimensions.

Embedding models generate vectors that represent aspects of the input's meaning.

### Example

Input:

```text
How can I reset my password?
```

Embedding model output:

```text
[0.12, -0.08, 0.41, 0.27, ...]
```

The numbers above are illustrative. Real embeddings contain values generated by the selected model.

A vector database stores these vectors and compares them using a configured similarity or distance metric.

### Important Terms

**Vector dimension:** The number of numerical values in a vector.

**Similarity metric:** A mathematical method used to compare vectors.

**Vector index:** A data structure that helps accelerate vector search.

**Nearest neighbors:** Vectors that are closest to a query vector under the selected metric.

**Metadata:** Additional information associated with a vector, such as its source, title, category, or chunk number.

## 6.3 How Does a Vector Database Work?

A typical vector database workflow contains two stages: indexing documents and retrieving information.

### Stage 1: Document Indexing

This process usually occurs before a user asks a question.

```text
Documents
    |
    v
Extract Text
    |
    v
Split Text into Chunks
    |
    v
Generate Embeddings
    |
    v
Store Vectors + Text + Metadata
    |
    v
Create or Update Search Index
```

### Step 1: Load Documents

The application loads files such as text documents, PDFs, Markdown files, or web pages.

### Step 2: Split Documents into Chunks

Large documents are divided into smaller passages.

For example:

```text
Document
    |
    +--> Chunk 1
    +--> Chunk 2
    +--> Chunk 3
```

Chunking helps the retrieval system return specific passages rather than entire documents.

### Step 3: Generate Embeddings

The embedding model converts each chunk into a vector.

### Step 4: Store the Data

The database stores the vectors and, depending on the system's design, the associated text and metadata.

### Stage 2: Query and Retrieval

This process occurs when a user asks a question.

```text
User Question
    |
    v
Generate Query Embedding
    |
    v
Search Vector Database
    |
    v
Rank Similar Vectors
    |
    v
Retrieve Relevant Chunks
    |
    v
Pass Context to the LLM
    |
    v
Generate Answer
```

### Important Point

A vector database does not automatically generate the final natural-language answer. A generative LLM usually performs that task.

## 6.4 Vector Database vs Traditional Database

Traditional databases are designed for structured records and queries. Vector databases focus on efficient similarity search over vector representations.

### Comparison

| Feature | Traditional Database | Vector Database |
|---|---|---|
| Main purpose | Store and query structured data | Store and search vectors |
| Typical query | Find a user by email | Find vectors similar to a query vector |
| Search method | SQL filters, indexes, and other query operations | Vector similarity or distance search |
| Metadata filtering | Common | Supported by many systems |
| Semantic retrieval | Requires additional techniques | A common use case |
| Example | PostgreSQL | Chroma |

These categories can overlap. Some traditional databases, including PostgreSQL with pgvector, can support vector similarity search alongside ordinary relational queries.

### Example Traditional Query

```sql
SELECT *
FROM users
WHERE email = 'user@example.com';
```

This retrieves records matching a specified email.

### Example Vector Search

```text
Find the 5 document vectors most similar to the user's query vector.
```

The database returns the nearest results according to the selected metric and search configuration.

### Key Learning

Traditional databases are excellent for structured queries. Vector search helps find content based on numerical representations of meaning.

## 6.5 Common Vector Database Options

Several tools support vector storage or similarity search. They are alternatives, not libraries that must all be installed together.

### 1. Chroma

Chroma is convenient for local development, learning, and RAG prototypes.

Features include:

- Vector storage and retrieval.
- Document and metadata storage.
- Similarity queries.
- Metadata filtering.
- Local persistent storage.

Common use cases:

- Learning embeddings.
- Building a local RAG prototype.
- Experimenting with document retrieval.

### 2. FAISS

FAISS is a library for efficient similarity search and clustering of dense vectors.

Features include:

- Multiple vector index types.
- Efficient similarity search.
- CPU and supported GPU implementations.
- Index persistence options.

FAISS is a search library rather than a full database service with every database feature built in. Applications often manage document text, metadata, and record identifiers separately.

### 3. Qdrant

Qdrant is a vector search engine that supports vector storage, payload metadata, filtering, and service-oriented deployment.

Common use cases:

- Applications requiring metadata filters.
- Persistent vector search services.
- Deployments that need a dedicated vector-search component.

### 4. pgvector

pgvector is a PostgreSQL extension that supports vector storage and similarity search.

Common use cases:

- Applications already using PostgreSQL.
- Combining relational data and vector search.
- Using SQL and metadata filters alongside vector operations.

### 5. Managed Vector Services

Managed vector services provide hosted vector-search infrastructure.

Potential benefits include:

- Less infrastructure administration.
- Managed scaling and maintenance.
- Hosted availability and operational support.

Consider pricing, data privacy, latency, vendor dependence, and deployment requirements before choosing a managed service.

### Comparison Table

| Option | Best Starting Point | Important Consideration |
|---|---|---|
| Chroma | Local RAG learning | Simple local persistence |
| FAISS | Learning vector indexing and search | Application manages other data as needed |
| Qdrant | Dedicated vector-search service | Deployment and operations |
| pgvector | Existing PostgreSQL applications | Database and index configuration |
| Managed vector service | Hosted production workloads | Cost, privacy, and service limits |



## 6.6 What Is a Vector Index?

A vector index is a data structure used to make similarity search faster.

Without an index, a simple implementation may compare the query vector with every stored vector.

This is called a linear or brute-force scan.

### Linear Search

```text
Query Vector
     |
     v
Compare with Vector 1
     |
     v
Compare with Vector 2
     |
     v
Compare with Vector 3
     |
     v
Continue through all vectors
     |
     v
Rank Results
```

For a large dataset, this can require substantial computation.

### Indexed Search

An index organizes the vector data to reduce the amount of work needed for a query.

Some popular approximate nearest-neighbor approaches include:

- HNSW: Hierarchical Navigable Small World graphs.
- IVF: Inverted File indexes.
- Product Quantization: A technique that compresses vectors to reduce storage requirements.

The available indexes depend on the database and its configuration.

### Exact vs Approximate Search

**Exact nearest-neighbor search** aims to return the true nearest vectors under the selected metric.

**Approximate nearest-neighbor (ANN) search** trades some retrieval accuracy for faster or more scalable search.

### Important Point

An index can improve retrieval performance, but it does not guarantee that the retrieved documents contain the correct answer.

## 6.7 What Is Metadata Filtering?

Metadata is additional information stored alongside a document or vector.

Examples include:

- Source filename.
- Document title.
- Page number.
- Topic.
- Publication date.
- Access permissions.
- Chunk index.

Metadata filtering restricts retrieval to records that satisfy specified conditions.

### Example Metadata

```json
{
  "source": "account-guide.md",
  "topic": "account",
  "page": 2,
  "chunk_index": 3
}
```

### Why Is Metadata Filtering Useful?

Suppose the knowledge base contains documents about accounts, billing, support, and training.

A user asks an account-related question. The application might filter by topic or access permissions before ranking results.

Metadata filters can improve relevance and help enforce application rules.

### Example

```python
results = collection.query(
    query_texts=["How do I reset my password?"],
    n_results=3,
    where={"topic": "account"},
)
```

This query searches for similar content among records matching the metadata condition.

### Important Security Note

Metadata filtering is not automatically a complete authorization system. For private or multi-user data, enforce access permissions correctly in the application and retrieval layer. Do not trust user-supplied filters to grant access to protected records.

## 6.8 What Is Persistence?

Persistence means data remains available after the program exits or restarts.

Without persistent storage, data stored only in memory may disappear when the application stops.

### In-Memory Storage

```text
Start Program
     |
     v
Create Collection
     |
     v
Insert Records
     |
     v
Stop Program
     |
     v
Data May Be Lost
```

### Persistent Storage

```text
Start Program
     |
     v
Open Persistent Database
     |
     v
Insert or Retrieve Records
     |
     v
Stop Program
     |
     v
Data Remains on Disk
     |
     v
Restart Program
     |
     v
Retrieve Existing Records
```

Chroma supports local persistence through `PersistentClient`.

Example:

```python
import chromadb

client = chromadb.PersistentClient(
    path="./data/chroma_demo"
)
```

The data is stored under the configured directory.

### Important Point

The application must reopen the same persistent database location to access the existing collection.

Persistent storage should also be backed up and managed appropriately for important data.

## 6.16 Common Vector Database Problems

### Problem 1: ModuleNotFoundError

Example:

```text
ModuleNotFoundError: No module named 'chromadb'
```

**Cause:** Chroma may not be installed in the active Python environment.

**Solution:**

```bash
python -m pip install chromadb
```

Check that the correct virtual environment is activated.

### Problem 2: Embedding Model Download Fails

**Cause:** The default embedding function may need to download model files.

**Solution:** Check network access and the configured model environment. For controlled or offline deployments, download and configure the embedding model explicitly before running the application.

### Problem 3: Vector Dimension Mismatch

**Cause:** The collection or index expects vectors with a different dimension from the vectors being inserted.

**Solution:** Use a consistent embedding model and vector dimension. Rebuild the index when migrating to an incompatible embedding model.

### Problem 4: Search Returns Irrelevant Documents

Possible causes:

- Poor chunking.
- Unsuitable embedding model.
- Weak query wording.
- Incorrect similarity configuration.
- Missing metadata filters.
- Irrelevant or low-quality source documents.

**Solution:** Inspect the retrieved text, evaluate the embedding model, improve chunking, and test alternative retrieval settings.

### Problem 5: Duplicate Records

**Cause:** The indexing script inserts records with new IDs every time it runs.

**Solution:** Use stable IDs and `upsert()` where appropriate.

### Problem 6: Data Is Missing After Restart

Possible causes:

- The script used an in-memory client.
- The database path changed.
- The collection name changed.
- Data was deleted.
- The application is running in another working directory and using a different relative path.

**Solution:** Use `PersistentClient`, verify the path, and confirm the same collection name is opened.

### Problem 7: Too Much Data Is Retrieved

**Cause:** The query requests too many results or the retrieval settings are not suitable.

**Solution:** Adjust `n_results`, add appropriate metadata filters, and evaluate whether reranking or relevance thresholds are needed.

## 6.17 Vector Database Best Practices

1. Use stable document and chunk IDs.
2. Store useful metadata with each chunk.
3. Keep the original source text or a reliable reference to it.
4. Use compatible embedding models for document indexing and query embedding.
5. Choose a suitable similarity metric.
6. Test retrieval with representative questions.
7. Measure retrieval quality rather than relying on a few examples.
8. Use metadata filters where they improve relevance or enforce access rules.
9. Back up important persistent data.
10. Rebuild or migrate the index carefully when changing embedding models.
11. Avoid storing sensitive information unless the system is designed and authorized to handle it.
12. Monitor storage, query latency, indexing time, and retrieval quality in production.

## 6.18 How Vector Databases Support Citations

A RAG application needs to know which original source supports a retrieved chunk.

For this reason, store source metadata alongside each chunk.

Example:

```json
{
  "id": "account-guide-chunk-003",
  "text": "Users can recover their account through password reset.",
  "metadata": {
    "source": "account-guide.md",
    "source_url": "https://example.com/account-guide",
    "page": 2,
    "chunk_index": 3
  }
}
```

The example URL is illustrative.

### Citation Workflow

```text
Retrieve Relevant Chunk
        |
        v
Read Source Metadata
        |
        v
Pass Chunk and Source to LLM
        |
        v
Generate Answer
        |
        v
Associate Claims with Sources
        |
        v
Return Answer with Citations
```

### Important Point

Storing source metadata makes citation handling possible, but it does not automatically guarantee correct citations.

The application must track the retrieved source, verify that it supports the answer, and render the citation correctly.

## 6.19 How to Choose a Vector Database for Production

The best choice depends on application requirements rather than popularity alone.

Evaluate:

### 1. Data Size

How many document chunks and vectors must be stored?

### 2. Query Volume

How many searches must the system handle per second?

### 3. Latency

How quickly should the system return relevant documents?

### 4. Filtering

Does the application require filters by source, user, permissions, category, or date?

### 5. Persistence and Backup

How will the data be stored, backed up, restored, and migrated?

### 6. Deployment

Should the system run locally, on a private server, or as a managed service?

### 7. Security

Does the application need authentication, authorization, encryption, or isolation between users?

### 8. Cost

Consider infrastructure, storage, network traffic, managed-service charges, and operational effort.

### 9. Evaluation

Test retrieval quality and performance using your own representative dataset.

### Key Learning

Choose the database that meets your retrieval, security, operational, and cost requirements. Do not assume one tool is best for every application.

## 6.20 Interview Questions and Answers

### Q1. What is a vector database?

A vector database stores and searches numerical vectors, often generated by embedding models, to retrieve similar items efficiently.

### Q2. Why are vector databases used in RAG?

They help retrieve document chunks that are semantically related to a user's question.

### Q3. What is the difference between an embedding model and a vector database?

An embedding model generates numerical vectors. A vector database stores and searches those vectors.

### Q4. What is metadata filtering?

Metadata filtering restricts eligible search results using attributes such as topic, source, date, or access category.

### Q5. What is persistence?

Persistence means that stored data remains available after the program exits or restarts.

### Q6. What is Chroma?

Chroma is a vector database that can be used to store embeddings, documents, and metadata and retrieve similar content.

### Q7. What is FAISS?

FAISS is a library for efficient vector similarity search and clustering. Applications may need additional components to manage text and metadata.

### Q8. What is the difference between Chroma and FAISS?

Chroma provides database-style functionality for collections, documents, metadata, and queries. FAISS focuses on vector indexing and similarity search.

### Q9. What is a vector index?

A vector index is a data structure that helps accelerate vector search.

### Q10. What is approximate nearest-neighbor search?

It is a search approach that trades some exactness for improved search speed or scalability.

### Q11. Does a vector database generate the final answer?

No. In a typical RAG application, it retrieves relevant information. A generative LLM generates the answer.

### Q12. Does a high similarity score guarantee a correct answer?

No. Similarity helps estimate relevance, but a retrieved passage may still be incorrect, incomplete, outdated, or insufficient.

### Q13. Why should metadata be stored with document chunks?

Metadata helps identify sources, filter records, track document locations, and support citation generation.

### Q14. Why should stable IDs be used?

Stable IDs allow applications to update existing records, avoid unnecessary duplicates, and identify specific chunks reliably.

### Q15. What happens when an embedding model changes?

The old vectors may be incompatible with the new model. The application generally needs to regenerate embeddings and rebuild or migrate the vector index.

## 6.21 Key Learning Summary

- A vector database stores and searches numerical vectors.
- Embedding models convert text into vectors.
- A vector database can store vectors alongside text and metadata.
- Similarity search retrieves vectors related to a query.
- Metadata filtering narrows retrieval to eligible records.
- Persistence allows stored data to survive application restarts.
- Vector indexes can improve search performance.
- Chroma, FAISS, Qdrant, pgvector, and managed vector services are different options.

- Source metadata helps applications produce citations.
